## 1.4. Scope and Limitations

The scope of the project covers the complete path from a participant's Spotify library to a generated, event-specific playlist. Users authenticate through Spotify OAuth, and their top tracks are collected upon login. Participants create or join shared events, and a natural-language event description drives semantic retrieval over the participants' indexed libraries, followed by AI wildcard generation, Spotify validation, and creation of the final playlist on the requesting user's account, together with per-participant contribution statistics. The system supports three interchangeable provider modes (gemini, college, and nim), allowing embedding, tagging, playlist generation, and query expansion to be served by different LLM backends. An automated evaluation harness for tuning retrieval parameters and prompts is included within scope, as is the full three-service web application (React client, NestJS orchestrator, FastAPI data engine).

Several limitations bound the delivered system. First, the application runs under Spotify Developer mode, in which each registered client permits only five authorized test users; the system pools the six team members' Client IDs — thirty users in total — and maps each registered user email to an assigned Client ID, but every user must still be pre-registered manually. Second, lyrics scraping may fail for some songs; the system degrades gracefully by embedding only the LLM-generated vibe tags. Third, the embedding provider cannot be changed after songs are indexed, since Gemini and the college model produce vectors of different dimensionality (3072 versus 384) and switching forces a full re-index. Fourth, the evaluation harness falls back to a built-in mock library of 20 songs when no real fixture is present, although headline evaluation runs used real event data. Fifth, prompt files produced by the evaluation loop are not applied automatically; they must be manually promoted to production, whereas tuned numeric parameters are loaded on every request. Finally, the college-hosted model enforces a five-requests-per-minute rate limit, constraining generation throughput.
