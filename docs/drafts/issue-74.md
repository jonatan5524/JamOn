## 1.5. Methodology

The project was developed iteratively in two-week sprints. Each sprint opened with backlog planning and closed with an internal team review followed by a meeting with the academic supervisor, so that direction could be corrected at fixed, short intervals throughout the project.

Within this cadence, the work progressed through the following stages. First, a literature and technology review was conducted, covering retrieval-augmented generation, LLM-based semantic tagging, hypothetical document embeddings, and vector search. Second, the system was designed as a three-service architecture with a strict separation of concerns: a NestJS orchestrator responsible for users, authentication, and Spotify integration, and a Python data engine responsible for LLM, vector, and scraping logic, with a React client on top. Third, the indexing pipeline was implemented — enrichment of tracks with lyrics and community tags, LLM vibe tagging, and embedding into a vector store. Fourth, the inference pipeline was built, adding HyDE query expansion, vector retrieval, and the LangGraph generation and validation workflow. Fifth, the provider layer was generalized into a multi-provider abstraction so that embedding, tagging, generation, and query expansion could each be served by a different LLM backend. Sixth, an automated evaluation harness was developed to tune retrieval parameters and prompts through grid search and prompt hill-climbing. Finally, the client application and end-to-end integration were completed.

Two vector stores are used deliberately rather than sequentially: ChromaDB serves local development and evaluation, while pgvector serves production. Both use cosine distance, so parameters calibrated during evaluation transfer directly to the production store.
