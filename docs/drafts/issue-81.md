## 3.4. Evaluation Metrics

The system is evaluated offline by an automated harness, whose experimental setup is described in Chapter 4. The harness scores every pipeline run on four metrics and combines them into composite scores whose weights differ between the two optimization phases. All formulas below are taken from the evaluation scorer implementation.

The alignment metric (45 percent of the full composite) measures the subjective quality that mechanical metrics cannot capture: whether the resulting tracklist actually fits the requested event. An LLM judge — NIM Llama-3.3-70b — receives the event description and the full tracklist and rates the playlist from 0 to 10 on three criteria: genre and mood match to the event, energy level appropriateness, and cohesion of the tracklist. The raw score is normalized to [0, 1]. No formal definition of playlist quality from the literature anchors the scale; it is anchored operationally by the three criteria stated in the judge prompt. If the judge call fails, a neutral 0.5 is returned so a transient API error does not corrupt an entire run.

The acceptance_rate metric (25 percent) is defined as the number of validated wildcards divided by the wildcard target, capped at 1.0. It quantifies the DJ model's hallucination rate: suggestions that Spotify cannot resolve to a real track lower the score.

The retrieval_relevance metric (15 percent) is the product of a precision term and a recall term. Precision, computed as one minus the mean cosine distance of the retrieved songs, rewards semantically tight retrieval. Recall, the fraction of requested result slots actually filled, penalizes over-strict distance thresholds that starve the pipeline of library material. The product punishes both failure modes: a configuration returning two perfect songs scores poorly on recall, while one returning many weak matches scores poorly on precision.

The size_fulfillment metric (15 percent) is the final playlist size divided by the target size, capped at 1.0. It guards against parameter combinations that produce small but seemingly high-quality playlists instead of filling the requested length.

The two phases weight these metrics differently. Phase 1, the 81-combination parameter grid search, uses a partial composite of 0.20 × acceptance_rate + 0.15 × retrieval_relevance + 0.15 × size_fulfillment, with a maximum of 0.5, deliberately excluding the judge: invoking an LLM judge for every event across all 81 combinations would be prohibitively expensive, and the mechanical metrics suffice to locate the structurally viable parameter region. Phase 2, prompt hill-climbing, uses the full composite of 0.45 × alignment + 0.25 × acceptance_rate + 0.15 × retrieval_relevance + 0.15 × size_fulfillment, with a maximum of 1.0. A guardrail handles a degenerate case: if every event in a run produces an empty library spine, the configuration is scored 0.0 rather than being allowed to appear healthy on generation metrics alone.

Finally, because evaluation runs do not call the real Spotify search, wildcard validation is replaced by a deterministic stub that rejects approximately 30 percent of candidates via an MD5 hash of the title and artist, matching the failure rate observed in production. Without this stub, acceptance_rate would be a flat constant and carry no optimization signal. Beyond the automated harness, evaluation was limited to manual testing by the team; no formal user surveys were conducted.
