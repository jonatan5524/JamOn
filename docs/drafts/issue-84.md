## 4.3 Data Analysis and Interpretation

The evaluation results demonstrate that the optimal system configuration was not the one utilizing the largest candidate pool or the strictest retrieval gate, but rather the configuration that balanced candidate diversity with a robust "library spine." The production parameter file reflects this balance with `n_results=5`, `max_distance=0.8`, `target_wildcards=7`, and `strong_match_margin=0.10`, corresponding to the third evaluation run on 18 June 2026. This setup achieved a Phase 1 partial score of 0.3966, a Phase 2 best composite of 0.8027, and a holdout composite of 0.6872.
The selection of `max_distance=0.8` confirms the necessity of a permissive absolute cosine-distance threshold. As project documentation notes, real text-embedding distances for relevant matches typically cluster within the 0.20 to 0.35 range. Because vector stores often return nearest neighbors even when semantically irrelevant, `max_distance` functions effectively as a coarse rejection gate. Stricter thresholds, such as 0.5 or 0.65, risked starving the retrieval pipeline. Thus, the winning configuration prioritized a permissive absolute gate, relying on relative spine logic to isolate the most coherent cluster within the returned set.
This prioritization of coherence over volume also explains the choice of `n_results=5`. While Phase 1 evaluated `n_results` values of 5, 15, and 30, the consistency of the June 18 runs selecting 5 suggests that larger candidate pools introduce noise more rapidly than they improve useful recall. This finding is consistent across headline runs—which utilized real event data seeded from production pgvector—and reinforces a core retrieval principle: once the nearest semantic cluster is identified, expanding the candidate list further risks diluting the "spine" and providing less coherent context to the DJ generation stage.
The Phase 2 score history for Run 3 further illuminates this trajectory, showing rapid improvement followed by a plateau. The composite score rose from 0.7300 to a peak of 0.8027, followed by minor oscillations. This pattern indicates that prompt hill-climbing quickly identified a superior prompt region, while later mutations yielded diminishing returns. The observed train-holdout gap of 0.1155—exceeding our 0.10 warning threshold—suggests mild overfitting to the eight training event descriptions. However, this should be interpreted as a manageable specialization rather than a failure; the holdout composite of 0.6872 confirms that the final configuration successfully transferred to unseen events.
Finally, the `target_wildcards=7` setting highlights the utility of "overproduction" to maintain playlist size. Given the deterministic validation stub, which rejects approximately 30 percent of wildcard candidates, requesting a surplus of suggestions provides the system with a buffer to absorb rejected entries without falling below the target length. In production, this is complemented by overprovisioning at the API level, ensuring the system remains resilient to Spotify URI resolution failures. Moving forward, these results suggest that future tuning should prioritize establishing stable retrieval parameters first, followed by short, holdout-validated prompt optimization to maintain broad generalization.
